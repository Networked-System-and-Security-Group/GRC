# CERNET 多网关与多路径：首轮验证

这轮分别回答三个问题：ACK 回另一个网关还能不能配对；两个网关各自限速是否会在共享瓶颈上相互影响；同一目的 DC 有多条 WAN 路径时，一条路堵了会不会牵连另一条。这里说的“控制器”是网关里按测得的延迟计算 `refRate`、通过 CNP 让发送端调速的 GRC 逻辑。实验设计、对照和判读条件见 [计划](plan.md)。

## 1. ACK 回到另一个网关

在呼和浩特 DC3 增加网关 327，和原网关 147 接到同一台 WAN 路由器。四条 `2 MiB` 流发往北京 DC0，两条走 147、两条走 327。固定前向路径，仅指定 ACK 回哪个网关。每组均完成 `4/4` 条流，无记录丢包，未启用镜像。这里默认的 `GSCC_ACK_TS` 模式使用目的网关的时间戳；样本包含从源网关出发到目的网关看到 ACK 的时段，也包含目的 DC 的处理和往返，不能直接当成纯 WAN 单程传播时延。

| ID | ACK 回程 | AckReq / 到达 ACK | 成功写表 | 未写入（槽位占用） | ACK 到达另一网关且原表项仍在 | 有效样本 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 94 | 全回原网关 | 212 / 212 | 60 | 152 | 0 | 60 |
| 95 | 两条流跨网关返回 | 212 / 212 | 60 | 152 | 30 | 30 |
| 96 | 四条流跨网关返回 | 212 / 212 | 60 | 152 | 60 | 0 |

按流 ID 和期望 ACK 序号关联写表及到达事件，另用网关 ID 和槽位重建当时的有效记录。分析脚本逐流检查写表和收到 ACK 的网关符合配置。**已写入且收到 ACK 的 60 个候选样本中，跨网关回程额外损失 0、30、60 个。** 原路返回也只有 `60/212 = 28.3%` 的请求产生样本；其余 152 次没有写表，不能归因于回程。全部跨网关时，发送端仍完成传输，源网关的 GRC 却没有采到样本。本轮只测无镜像的故障对照，四条流的回程比例和有限哈希表命中率都不能外推到真实 DC。

后续在服务器上补做了快慢镜像对照，比较样本恢复、额外流量和更新时间，见[双网关 ACK 镜像](../../../expr-1121-ack-mirror/report.md)。

## 2. 两个网关各自限速会不会竞争

呼和浩特到北京的骨干链路设为名义 `200 Gb/s`，网关接入保留 `400 Gb/s`，ACK 全部返回原出口。两批各四条 `384 MiB` 长流，第二批在 `15 ms` 加入。单网关和同 DC 双网关采用相同的源、目的主机、流量与流启动时间，只切换第二批的出口。双源 DC 参照把第二批移至呼和浩特的 DC4（网关 184），源端交换资源不同。关闭权重的组各自更新参考速率；默认权重组仍使用仿真中的全局 `k`，作为默认配置结果，不能称为完全无共享状态。

| ID | 第二批发送位置 | 权重 | 瓶颈吞吐，60–100 ms（Gb/s） | 队列平均 / 峰值，60–100 ms（MiB） |
| --- | --- | --- | ---: | ---: |
| 97 | DC3 原网关 | 关闭 | 155.9 | 8.0 / 32.6 |
| 98 | DC3 第二网关 | 关闭 | 191.0 | 11.8 / 59.2 |
| 99 | DC4 唯一网关 | 关闭 | 194.9 | 16.0 / 54.0 |
| 100 | DC3 原网关 | 默认 | 132.9 | 11.8 / 85.9 |
| 101 | DC3 第二网关 | 默认 | 182.8 | 24.9 / 115.9 |

`22–45 ms` 内，无权重的单网关几乎无骨干排队，双网关的平均队列已有 `19.2 MiB`。在 `60–100 ms` 无权重双网关两条接入的平均发送速率约为 `100.0 / 103.6 Gb/s`，双源 DC 参照约为 `101.3 / 102.1 Gb/s`；都是共用一个骨干瓶颈的相似现象。同 DC 双网关的总吞吐更接近瓶颈容量，但队列更深，两边确实通过共享队列相互影响。五组均 `8/8` 完成、无记录丢包、无 PFC pause，所得是有限时间内的吞吐与排队证据，不能证明独立限速总能平稳收敛。

[吞吐、队列和各网关参考速率](shared-bottleneck.svg)。发送量按出队事件计数，每 `0.5 ms` 汇总，队列每 `1 ms` 采样。现有 Qbb 发送时间转换为整数纳秒时向下取整；对于满长包，这里的饱和采样可略高于名义 `200 Gb/s`（如约 `204.5 Gb/s`）。判断过载以接入发送量、骨干队列和各组相对变化为准，没有把高于名义速率的出队计数当作物理容量。

**权重和速率波动。** 固定权重组取 `w=1`。自适应版本希望一个承载更多并发流的网关—目的 DC 流量组获得更大的带宽份额。代码用最近的 GRC 降速通知比例和参考速率估算权重，启用后初始为 `2.5`，随后用仿真全局的 `k` 做归一化，限制在 `[1,4]`。在排队估计相同的情况下，`w` 翻倍会使内部目标速率 `w/(δq)` 翻倍，线性更新步长也随 `w` 增大。实际吞吐还取决于队列、快速降速分支和发送端响应。第 100 组的快速降速比第 97 组早（第 `50` 对 `71 ms`），两组在 `60–100 ms` 窗口内经历的排队和降速阶段不同。这个窗口的均值不足以判断自适应权重的长期吞吐高低。

第 97 组在 `71 ms` 估计的排队时延升至 `0.27 ms`，内部目标约 `187 Gb/s`，低于当时约 `247 Gb/s` 的参考速率，触发连续快速降速。`71 ms` 的瓶颈出端口还积压 `26.9 MiB`，因此链路继续满载。到 `80.5 ms` 的吞吐采样仍约 `204.5 Gb/s`，`81 ms` 队列读数归零，同一采样点的吞吐降至 `120.9 Gb/s`。第一条流到约 `171.8 ms` 才完成。`86 ms` 排队估计回落，GRC 又开始上调。这个时间顺序解释了为何单网关也会出现“上调、积压、快速降速、排空、再上调”。

一个简化的稳态推导可以说明两种部署何时相似。假设几个网关都只看到同一个瓶颈的排队延迟 `q`，权重 `w_i` 固定，且实际速率已跟上 `w_i/(δq)` 这个目标。若瓶颈一直在忙、队列又不再上涨，合计实际速率就等于容量 `C`，由此得到 `q = Σw_i/(δC)`。比较同 DC 双网关与双源 DC 时，DC 标签不出现在这个式子里；两者若有相同的瓶颈、排队信号和权重，就有相同的理想稳态。排队反馈本身没有被消掉：把一个权重为 1 的出口拆成两个权重各为 1 的出口，简化模型里的总权重会翻倍。这个推导预先假定已经到达稳态，且未包含路径间观测差异、更新滞后、权重估计和 CNP 到实际发包速率的响应，不能拿来证明真实 GRC 会收敛，也不能拿来精确预测上述队列数值。

## 3. 同一目的 DC 有多条 WAN 路径

用 CERNET 已有的北京→石家庄直达路和北京→天津→石家庄绕行路。各骨干段设为 `100 Gb/s`，共同接入仍为 `400 Gb/s`。北京 DC0 的八条 `256 MiB` 流分到两条路径，仍共用同一个目的 DC 的 `refRate`，关闭自适应权重。103 组在 `25 ms` 时从北京 WAN 侧主机 227 启动一条 `192 MiB` RDMA 背景流，目的为石家庄 WAN 侧主机 267；背景流只经过直达骨干，既不经过源 GRC，也不走两端 DC 接入。背景流启动前两组的吞吐和队列采样一致。

| ID | 对照 | 直达路 RDMA（Gb/s） | 经天津 RDMA（Gb/s） | 直达队列均值（MiB） | 共用 `refRate`（Gb/s） | 发给经天津流的 GRC CNP |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 102 | 无背景流 | 65.9 | 64.8 | <0.001 | 130.7 | 315 |
| 103 | 仅直达路增加背景流 | 44.0 | 41.0 | 16.2 | 85.7 | 512 |

表中时间窗为 `30–42 ms`。103 组背景流平均约 `57.0 Gb/s`，经天津的两段骨干及两端接入在窗口内队列采样均为零。**经天津的吞吐仍下降约 37%，同时源网关向这些流发了更多 CNP，支持“按目的 DC 汇总限速会牵连另一条未拥塞路径”。** 此处证实已有聚合控制的缺点，尚未测路径级控制的改进幅度。[两条路径的时间序列](two-paths.svg)。

这里的队列读数来自 `buffer_monitor`。每隔 `1 ms`，它读取相应链路的发送端口上等候发出的字节数（本对照关注 RDMA 数据所在的队列）。连续采样为零说明这些端口没有观测到持续积压。采样点之间可能有短暂排队，链路上也可以照常有数据在传。GRC 的 ACK 配对记录在另一个表里，队列读数无法说明配对表是否有记录。

另设无拥塞的延迟对照。106、107 先用一条 `48 MiB` 直达流建立历史最小时延；在 `25 ms` 加一条 `2 MiB` 流，分别走直达或经天津。测量的目的网关时间戳差中位数为 `1.936 / 2.474 ms`，差 `0.537 ms`，与骨干传播差相符。两组骨干及接入的队列采样均为零；直达对照到达后估计排队为 `0.01 ms`（下限），`refRate` 从 `100.0` 升到 `102.7 Gb/s`；经天津后估计排队为 `0.54 ms`，`refRate` 从 `100.0` 降到 `91.2 Gb/s`。这是新流换用另一条固定路径，并非对在途流做动态重路由。104、105 为预实验：第一条 `2 MiB` 流未达到初始化要求，没能建立短路基准，只用于核对传播差，不用于解释降速。

## 复现与归档

`multi-gateway` 从 `dev` 的 `0b56ab0` 重建，旧提交仍由 `P4-fix` 保留。新增 `extra_dci_switches` 和 `pinned_wan_paths`，只给明确配置的主机对固定正向和反向路径，其他流量保留原路由；实验路径按正反向实际传播计算基准 RTT。原 CERNET JSON 和 GRC 控制律未改。`rate_monitor` 增加 `switch_id`，`WAN_TRACE_RTT_MATCH=1` 开启配对日志；配置了固定路径时，`link_utilization` 在出队计数。

在仓库根目录执行 `bash expr-1121-multi-gateway-wan/run.sh`，可附 case 名挑选运行，默认 seed 为 1。依赖安装与分析：

```bash
uv venv .venv
uv pip install --python .venv/bin/python pandas matplotlib ipython
.venv/bin/python expr-1121-multi-gateway-wan/analyze.py {94..107}
```

复跑时使用实际分配的 ID。预实验 104/105 如需重跑，可指定 `path-short path-long`。分析入口使用 `analysis.deep_analyse.get_analyser` 读取配置，核对数据实际经过的 WAN 链路和 ACK 归属，并生成 [汇总数据](summary.json)。本机 94–107 共 14 组全部正常结束；另用未经派生的 `config/cernet_topo.txt` 跑了兼容性冒烟（108，`4/4` 条流完成）。原始日志保留在 `mix/output/`。首轮在本机执行，后续镜像实验在 `pengbo29@192.168.5.112:/home/pengbo29/grc` 执行。两轮原始日志分别保留在各自的运行机器上。

当前结论限于静态路由、所用负载和一次随机种子。原审稿意见还涉及镜像的额外流量、顺序、状态一致性和网关数扩展，以及在途流换路与故障切换。这轮分别隔离了无镜像的配对失败、共享瓶颈上的相互影响、目的 DC 聚合限速的牵连，尚未验证镜像开销、动态切路、路径级控制或普遍稳定性。
