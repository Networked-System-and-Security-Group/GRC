## 2. 重要实验路径与结论

### 2.1 长距单流场景

基于 `cernet_topo_longloss_001` 相关拓扑做过多轮单流实验：

- `0.1%` loss
- `fec=0/1` 对照
- 开启 `FEC_LOG=TRUE`

关键现象：

- 原始长距拓扑下，`fec=1` 与 `fec=0` 几乎无差异，`finish_time` 只差微秒级
- 即使把 WAN-WAN 核心链路统一提升到 `2500us`
  - 新拓扑：`config/cernet_topo_longloss_001_ge2500us.txt`
  - 结果仍然几乎无差异

关键结论：

- 仅靠更长 RTT，在 `0.1%` 这种较低 loss 下，并不能让当前 FEC 显示出明显收益
- 这说明收益阈值更可能由 loss 形态主导，而不是单纯由 RTT 主导

### 2.2 仓库原本纯 RDMA 拓扑 / 流量实验

为了避免拿定制场景误判，后面切回仓库原本纯 RDMA 入口：

- 拓扑：`config/cernet_topo.txt`
- 流量：`config/w-dynamic-100-150.txt`
- 显式关闭 TCP：`--tcp_flow ''`

中途现象：

- `DropInfo` 一直是 `0 0`
- `fec=1` 没有看到稳定领先
- 中途完成流数常常略落后于 `fec=0`

结论：

- 在这组默认纯 RDMA 场景中，没有证据表明 FEC 有收益
- 更像是“无丢包时只引入了额外冗余开销”

### 2.3 更大默认纯 RDMA 流量：`w-dynamic-150-180`

用户要求换更大的流量，于是停止 `w-dynamic-100-150` 实验，重新跑：

- `cernet_topo`
- `w-dynamic-150-180`
- `pure RDMA`
- `fec=0/1`

当前对应输出目录：

- `mix/output/[184]-05-08-09:06:37`
- `mix/output/[185]-05-08-09:06:37`

重要发现：

- 这组不是无丢包
- `drop_log` 中已经有大量丢包
- 丢包几乎全部集中在 `switch 225`

中途统计：

- `fec=0`: 当前统计到 `191,861` 次 drop
- `fec=1`: 当前统计到 `218,180` 次 drop

说明：

- FEC 打开后，当前阶段热点拥塞反而更重
- repair 包进一步加压了热点出口

同时，`fec=1` 的 `fec_log` 中可以看到：

- `rx_group_recovered=755`
- `tx_nack=623`
- `rx_nack_sender=378`
- `tx_group_rewind=381`
- `tx_group_resume=215`

结论：

- 当前 FEC 并不是完全没有参与恢复
- 但恢复效果不足以抵消额外冗余和热点拥塞
- 并且 sender / receiver 状态机仍然存在逻辑问题，所以这组结果不能直接当成“可靠性能结论”

另外，这组实验截至当前仍未自然结束：

- `flow_output` 还没有最终落盘
- 对应进程仍在运行

因此这组暂时只能做“过程分析”，不能给最终 FCT 汇总结论

## 3. 之前已经修过的 FEC 问题

在这轮对话之前和早期实验中，已经修过几类明确问题，当前仍保留在代码里：

1. 接收端 ACK advancement 不再依赖 stale 的 `next_expected_group_id`
   - 改为按 `ReceiverNextExpectedSeq` 查找覆盖该 seq 的 recoverable group

2. `GetNxtPacket()` 中 FEC metadata 覆盖问题
   - 之前存在 packet tag 被旧值重新覆盖的 bug

3. sender 侧 false cumulative ACK bug

4. 错误 group 的 NACK control-tag 问题
   - 引入 `PopulateFecControlTagForExpectedSeq()`

这些修复主要解决了：

- tail stuck / 无法结束
- FEC metadata 错乱
- sender 错误“提前完成”

但它们没有解决这轮重新审查中暴露出的更深层状态机问题

## 4. 这轮重新审查中确认的问题

### 4.1 不是“真实 FEC 解码”

当前 receiver 在 `ReceiveFecData()` / `ReceiveFecRepair()` 中只用：

- `group.total_received >= group.m_snapshot`

来判定 `recoverable`

然后在 `TryAdvanceFecAck()` 中直接：

- 把 `ReceiverNextExpectedSeq` 推到 `group.data_end_seq`

这意味着：

- 没有真正恢复缺失 data
- 没有真正重构缺洞
- 更像“组级 ACK 跳过模拟”

这本身不一定是 bug，因为用户已经明确说明“只需要模拟 fec 即可”

但它需要在文档中诚实表述：

- 当前实现是“FEC 模拟”
- 不是“真实编码/解码”

### 4.2 sender NACK rewind 错误回退 `snd_una`

这是本轮确认的最严重错误之一。

`RewindFecGroupForNack()` 原本会：

- `qp->snd_una = target->data_start_seq`
- `qp->snd_nxt = target->data_start_seq`

这会让 sender 侧累计 ACK 边界倒退，破坏 ACK 单调不减语义。

这在逻辑上是错的，即使只做 FEC 模拟也不应该发生。

### 4.3 repair 在途计数记账不闭合

原实现中：

- 每发送一个 repair 包都 `outstanding_repair_pkts++`
- prune 时只按组减一次 `n_snapshot`

一旦组被 rewind / repair 重发：

- 在途 repair 会被重复累计
- `GetOnTheFly()` 会高估窗口占用
- 进而污染发送窗口、完成判定和节奏

### 4.4 receiver FEC group 没有生命周期回收

`rxQp->fec.groups` 一直积累，之前没有在 ACK 稳定跨过 group 后 `erase`

后果：

- 状态长期膨胀
- 旧 group 继续参与查找
- `ClearFecAckEmittedFlags()` 反复全量遍历
- `fec_log` 爆炸性增长

当前大实验中：

- `mix/output/[185]-05-08-09:06:37/fec_log`
  已增长到约 `8.3GB`

### 4.5 timeout recovery 会整体清空 sender FEC 状态

`ResetFecStateForRecovery()` 当前的设计是：

- 清空 active group
- 清空 outstanding groups
- 清空 repair 在途计数

这与普通 RDMA recovery 对齐，但有副作用：

- 如果网络中仍有旧的 FEC ACK/NACK 在飞
- sender 可能已经找不到对应组状态

这目前仍然是一个已知风险，而非已完全解决的问题

### 4.6 `ack_emitted` 没有形成稳定幂等保护

代码里虽然有：

- `group.ack_emitted = true`

但后面经常又 `ClearFecAckEmittedFlags()` 全量清掉

所以它更像调试字段，而不是严谨的控制状态

## 5. 这轮已经完成的代码修复

本轮我实际改了以下代码：

- `src/point-to-point/model/rdma-hw.cc`
- `src/point-to-point/model/rdma-queue-pair.h`

### 5.1 修复 NACK rewind 不再回退 `snd_una`

现在 FEC 组回退时：

- 只回退 `snd_nxt`
- 不再回退 `snd_una`

目的：

- 保持 sender 侧累计 ACK 单调不减

### 5.2 repair 在途计数改为按组一次性记账

在 `FecTxGroupState` 新增：

- `repair_counted_inflight`

逻辑变为：

- repair 首次发送时按组一次性将 `n_snapshot` 计入在途
- 重传 repair 不再重复累计
- prune 组时只回收一次

### 5.3 receiver 端补上 group 回收

新增：

- `PruneAckedFecRxGroups()`

当 ACK 因 FEC 组前推后：

- 回收所有 `data_end_seq <= ReceiverNextExpectedSeq` 的旧 group

目的：

- 避免 `rxQp->fec.groups` 无限膨胀
- 降低旧 group 干扰后续控制 tag 查找的风险

### 5.4 timeout recovery 同步清理 retransmit resume 状态

`ResetFecStateForRecovery()` 现在同时：

- 清理 `retransmit_resume_valid`
- 清理 `retransmit_resume_snd_nxt`
- 清理 `retransmit_group_id`

避免悬空恢复点残留

### 5.5 编译验证

修改后已执行：

- `./waf build`

结果：

- 编译通过
